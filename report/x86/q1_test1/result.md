# 課題1 result.md

## 1. プログラムコード (test1.asm)

```nasm
global _start
section .text
_start:
    mov rax, 10
    mov rbx, 20
    add rax, rbx
```

## 2. 説明

`rax` に 10、`rbx` に 20 を格納し、`add rax, rbx` で加算して `rax = 30` にするだけの単純なプログラムである。
ビルドは最適化オフ（アセンブラレベルではデフォルトの立式）で行い、NASM が `mov` 命令をどのようにエンコードするかを観察する。

```
nasm -O0 -f elf64 -o test1.o test1.asm
ld -o test1 test1.o
```

## 3. 実行ログ（逆アセンブル結果）

```
$ objdump -d -Mintel test1

test1:     file format elf64-x86-64

Disassembly of section .text:

0000000000401000 <_start>:
  401000:	48 b8 0a 00 00 00 00 	movabs rax,0xa
  401007:	00 00 00
  40100a:	48 bb 14 00 00 00 00 	movabs rbx,0x14
  401011:	00 00 00
  401014:	48 01 d8             	add    rax,rbx
```

## 4. バイナリ対応表

| アドレス | 機械語Hex | アセンブリ命令 | 説明 |
|---|---|---|---|
| 401000 | `48 b8 0a 00 00 00 00 00 00 00` | `movabs rax, 0xa` | REXプレフィックス(48) + オペコード(b8) + 64bit即値(8バイト)。合計10バイト |
| 40100a | `48 bb 14 00 00 00 00 00 00 00` | `movabs rbx, 0x14` | REXプレフィックス(48) + オペコード(bb) + 64bit即値(8バイト)。合計10バイト |
| 401014 | `48 01 d8` | `add rax, rbx` | REXプレフィックス(48) + オペコード(01) + ModRM(d8)。合計3バイト |

## 5. 考察: 各 mov 命令が10バイト消費する理由

NASM はソース上の `mov rax, 10` を、即値を64ビットレジスタへ格納する命令として解釈し、`movabs rax, imm64` 相当の命令にアセンブルする。
このエンコーディングは以下の構成で合計 **10バイト** になる。

- **REXプレフィックス**: `48` (1バイト) — 64bit操作であることを示す `REX.W` ビットを立てるために必要。
- **オペコード**: `b8`〜`bf` (1バイト) — 「レジスタに64bit即値をロードする (MOV r64, imm64)」命令。レジスタ番号はオペコード自体に埋め込まれる（`rax`なら`b8`、`rbx`なら`bb`）。
- **即値 (imm64)**: 8バイト — 64bit幅の即値をリトルエンディアンでそのまま埋め込む。10 は `0a 00 00 00 00 00 00 00`。

合計: 1(REX) + 1(オペコード) + 8(即値) = **10バイト**。

一方、`add rax, rbx` はレジスタ間演算のため即値を持たず、REX(1) + オペコード(1) + ModRM(1) = 3バイトで済んでいる。
もし即値が32bit以内に収まるのであれば、`mov eax, 10` のように32bitレジスタへの書き込み命令（オペコード `b8` + 32bit即値、REX不要）で5バイトに短縮できる（課題2で詳述）。
しかし今回は `mov rax, 10` のように64bitレジスタを明示したため、NASMは「64bit全体に即値をロードする」ことを安全側に倒して `movabs`（10バイト版）にエンコードした。これが最適化オフ時に各mov命令が10バイトを消費する理由である。
